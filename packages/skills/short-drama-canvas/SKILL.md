# 短剧画布施工

本技能是创作文档与 Toonflow 画布之间的唯一通道。创作事实仍住在项目 Markdown 里，
画布只是它们的执行形态：节点承载提示词与参数，连线复现文档已经写明的参考关系。

不创造上游没有的内容。文档里没写的镜头、参考、参数，不在画布上补齐。

## Quick Start

先跑一遍施工计划，把文档解析成节点清单与连线清单：

```bash
python3 {技能目录}/scripts/board_plan.py <project> --episode <EP> --pretty
```

脚本只读文档、只输出计划，不写文件、不碰画布、不调用供应商。拿到计划后再询问
**目标模型**（图片、视频、对白音频、配乐各一个），因为它决定 `providerId`/`modelId` 与可用档位：
先用 `getCanvas({include:["nodeTypes"]})` 确认画布实际启用了哪些节点类型，
再用节点的 `node:getConfig` 读该节点实际可用的模型与档位。不替创作者默认选模型。

计划里几处需要留意：

- `stats.dangling_items` 非空：文档引用了不存在的条目，回对应 owner 修文档，不在画布上猜。
- `stats.empty_prompts` 非空：条目缺可复制提示词，同样回 owner 补。
- `stats.unready_references` 非空：这些条目的参考图还没备齐，看每条的 `state`——
  `待补参考图` 是缺图（`missing` 列出缺口点名的条目），`待解析` 是那一行读不出槽位。
  **建节点可以继续，但这一镜不能声称已有参考，也不能拿去生成。**
- `stats.music_without_style` / `music_without_duration` 非空：乐段缺风格描述（节点唯一
  进模型的文本），或定不出时长上限；先回 `$short-drama-video-prompts` 把章节写全。
- `stats.unresolved_references` 非空：这些参考槽位点到的名字在项目里没有条目，多是创作者
  自己在项目外准备的素材（`输入/参考图/…`）。画布不替它造节点，所以这些参考**不会出现在
  连线里**，要由创作者在画布上自行挂——如实转告，不静默丢。
- `stats.music_lyrics_pending` 非空：这些乐段的歌词还标着待补，节点现在只出纯旋律；
  `stats.music_with_lyrics` 列出的是主题曲（歌词会随节点一起进模型），付费前先核对歌词。
- `stats.incomplete_reference_slots` 非空：这些参考缺语义声明（用途 / 控制 / 不得控制 /
  中文名称），编译不出参考约束，执行端收不到保留要求——回上游补全，不在画布上编。
- `stats.reference_over_limit` 非空：声明的素材数超过目标模型一次生成的上限（H3：9 图 /
  3 视频 / 3 音频），回分镜阶段按重要性取舍，不在提示词里假装它们仍然生效。

每个带参考的节点上都有 `reference_ready`：只有它为真（有图且没缺口，或创作者明确选择无参考）
才算这一镜的参考备齐，`reference_state` 只说明是哪一种情况。

## 画幅：项目开始时定一次

成片画幅不是每镜的独立选项，它是**项目级事实**，住在 `short-drama.json` 的 `format.aspect_ratio`，
由 `$short-drama` 在项目初始化时与创作者确认一次（该脚本属于 `$short-drama` 技能）：

```bash
python3 <short-drama>/scripts/project_tool.py init <project> --title "<标题>" --aspect-ratio 9:16
```

之后所有阶段都从档案读它，**不再逐镜询问、也不逐节点调整**。确认一次，全流程沿用。

项目已经建好、画幅当时留了 `unset`，或要变更画幅时，用本技能的读数/写值脚本，不必重建项目：

```bash
python3 {技能目录}/scripts/board_ratio.py <project>            # 读：档案值、视觉设定值、是否冲突
python3 {技能目录}/scripts/board_ratio.py <project> --set 9:16 # 写：改档案的成片画幅
```

`board_plan.py` 已经按这个顺序取值：项目档案 → `视觉设定.md` → 都没有才报缺失。
两处不一致时以**档案**为准，并在 `stats.ratio_conflict` 里如实报出，请创作者回对应 owner 统一文档。
`stats.ratio_missing` 为真说明画幅还没定：**先问一次并写入档案**，不要靠默认值建图。
`stats.nodes_without_ratio` 列出具体哪些节点没定出画幅。

⚠️ **画幅没定出来时 `board_apply.py` 拒绝导出**（返回码 3）。这不是缺值而是**错值**：脚本不写
`ratio` 时，节点会沿用自身的默认比例（视频 `16:9`、图片 `1:1`）——一部别的画幅的片子会整套
按错比例出图，而画布上看不出任何异样。确认画幅并写入档案后再导出；确实要先看节点时加
`--allow-missing-ratio` 显式放行，那些节点会沿用自身默认值。

进画布时的应用范围：

| 节点 | 画幅 | 原因 |
|---|---|---|
| `SHOT-*` 关键帧 | 成片画幅（如 `9:16`） | 它就是成片的画格 |
| `MOTION-*` 视频 | 成片画幅 | 同上 |
| `IMG-*` 资产板 | `自适应`，或条目「画幅」字段显式指定 | 资产板是素材，出图比例由条目自己决定，不受成片画幅约束 |

`IMG-*` 的 `ratio` 默认是 `自适应`（写死的常值，不读成片画幅）。条目要让生成端锁定一个
确定比例时，在条目里写 `- 画幅：4:3`，脚本会取该字段里的比例覆盖 `自适应`；
字段缺失或写不出比例就仍是 `自适应`。**同一批资产板里只用一种**，混用会让同批参考图
结构不统一。

`SHOT-*` 与 `MOTION-*` 在个别人物特写或构图另有要求时，也可在条目「画幅」字段里写明覆盖
成片画幅——但那是例外，不是常规路径；没有该字段就一律沿用档案值。

改画幅属于项目级决定：由 `$short-drama` 走创作者决策流程改写档案，再重新导出画布，
不在画布上逐节点改 `ratio`。

## 条目到节点

四类条目对应四类节点，节点类型名以 `getCanvas` 返回的 `availableNodeTypes` 为准
（本机形态为 `remote-comfyuiImageNode`、`remote-comfyuiVideoNode`、`remote-comfyuiAudioNode`、
`remote-comfyuiMusicNode`）。文档里没有对应条目的东西**不建节点**——参考槽位里那些项目外的
素材文件也一样，见「连线」节。

| 文档条目 | 节点 | 提示词取 | 参数 |
|---|---|---|---|
| `图片提示词.md` 的 `IMG-*` | 图片节点 | `### 可复制提示词` 正文 | `ratio` 见上节：条目「画幅」字段有值就取它，没有就是 `自适应`；`megapixels` 取 `getConfig` 返回的档位 |
| `分镜.md` 的 `SHOT-*` | 图片节点 | `### 冻结关键帧提示词` 正文 | `ratio` 取档案的成片画幅；`megapixels` 同上 |
| `视频提示词.md` 的 `MOTION-*` | 视频节点 | `### 可复制提示词` 正文 | `duration` 取「时长」；`ratio` 取档案的成片画幅 |
| 录音表的每条台词 | 音频节点 | `line_text`（台词原文） | `instruction` 取 `tactic` 与专名发音注记；`channel` 为 `VO`/`OS` 时标进标签 |
| `视频提示词.md` 的时间线音乐章节 `MUS-*` | 音乐节点 | 风格描述（章节里的围栏块或「风格描述」字段） | `maxDuration` 取「时长」，章节没写就按「使用区间」换算；`lyrics` 只取章节里 `- 歌词：` 定稿的文本（主题曲），写「无（纯旋律）」就留空 |

视频节点的 `mode` **不从文档写**：它是供应商声明的档位（`text`/`singleImage`/…），
哪个可用由所选模型决定，按 `node:getConfig` 读。文档的「生成方式」（图生视频/文生视频）
是**创作阶段的路径选择**，说的是这一镜走不走参考图，不是节点上的档位值——两者不是同一层。

**音乐条目的正文是风格描述**：音乐节点没有可复制提示词，它唯一进模型的文本就是风格描述。
乐段怎么切、风格怎么写、时长怎么定，见 [乐段设计](references/segment-design.md)——那是给
写时间线音乐章节的人看的，章节本身归 `$short-drama-video-prompts`。

**歌词只在章节给了定稿文本时才带**：写 `- 歌词：<文本>`（或 `- 歌词：见下` 加一个围栏块）
就是主题曲，歌词原样进节点；写 `- 歌词：无（纯旋律）` 就是纯配乐，`lyrics` 留空；写「待补」
说明还没定稿，只出纯旋律并报进 `stats.music_lyrics_pending`。画布**不代写歌词**，也不放开
供应商代写——歌词必须来自创作者提供或明确接受的文本（上游原文）。

对白与音乐都来自 `$short-drama-write`／`$short-drama-video-prompts` 已定稿的文档：
录音表逐句台词是台词的机械投影（台词权威仍是《剧本.md》），时间线音乐章节是配乐的设计落点。
两者都在文档里定稿，画布只把它们读成节点，不改词、不切乐段。

**对白只挂音色不给语气，模型会照稿念成播音腔**。所以每个对白节点的 `instruction` 必须带上
录音表的 `tactic`（可执行的策略，不是情绪词）与专名发音注记；同一角色的每一句都挂**同一段**
参考音色（`参考音频` 行里写的角色名决定挂到谁的对白节点上）。音色是参考不是成品音轨：
它接对白节点的 `in`，不接视频节点。

提示词正文以 `>` 开头的引用块形式存在，写进节点时去掉行首引用标记，保留正文原样，
不改写、不压缩、不翻译。节点标签用条目 ID 与标题，如 `SHOT-EP001-002 · 四个号，四个粉`。

参数一律先 `node:getConfig` 读当前值与可选范围，再 `node:setConfig` 写入，
`providerId` 与 `modelId` 成对提供。档位只取 `getConfig` 返回值里实际存在的项；
目标节点没有对应字段时说明缺项，不把参数硬塞进提示词。

## 连线

连线依据全部来自文档，分两类，语义不同，不要混为一谈：

**结构性连线**（`MOTION-*` 的「分镜」字段指向的 `SHOT-*`）：关键帧节点连到视频节点，
表示这一镜的画面来源。文档写了就必连，不因创作者选择文生视频而断开——
文生视频说的是不送参考图，不是这一镜与关键帧无关。

**参考性连线**（`SHOT-*` 的「图片提示词项」字段列出的 `IMG-*`）：资产图节点连到关键帧节点。
这类连线表达的是**计划中的引用结构**，建图时就该连上，否则关键帧节点不知道该拿哪张板当参考。
它与文档里那条「文件此刻在不在项目里」的轴不是一回事：

- **画布连线**＝这一镜打算接哪几张图，属于施工图，随节点一起建；
- **《分镜.md》的「输入参考图」**＝这次实际送哪些图片：`REF-...` 是项目里已有的真实文件，
  `PLAN-...` 是创作者在生成时自行挂载的图；两者都是「打算」，都不等于文件此刻可读。

两者不矛盾，但生成有先后：**先出资产板，再出关键帧，最后出视频**。资产板还没生成时，
连着的关键帧节点会因为没有图而生成失败——这正是顺序约束在起作用，不是配置错误。

「图片提示词项」与「输入参考图」是两条独立的轴：前者说这一镜打算用哪些资产图，
后者说这次实际送哪些图片。`输入参考图` 为 `无（创作者已明确选择文生视频）` 时，
结构性连线照连，参考性连线按上一条判断。

**参考槽位连线**：`分镜.md`／`视频提示词.md` 的「输入参考图」与 IMG 条目的「参考」是同一套
语法（上游校验器也是同一个），两类槽位都**只按名字认节点**：

- `PLAN-*` 的定位符就是**条目 ID**（`IMG-...`／`SHOT-...`）——文档已写明「这张图画的是哪一条
  已决定的事实」，直接用定位符找到那个条目；
- `REF-*` 的定位符是**项目内的真实文件路径**，靠**名字**认出它是哪一条的产出，依次看
  《中文名称》里出现的条目 ID（上游样例 `《SHOT-EP001-002 起始帧》`）、路径的文件主名
  （`制作成果/images/SHOT-EP001-002.png`，文件名就是产出它的条目）、以及《中文名称》是否
  恰好是某个条目的标题。

**边只表达节点之间的关系**，不表达「这个节点当前显示第几次生成的结果」。所以**不为参考文件
另建节点**——画布上不需要一个挂着文件的旁支节点，用它自己在画布上的那个节点就够了。

名字里**认不出条目**（如 `输入/参考图/江辰定妆.jpg《江辰定妆照》` 这种创作者在项目外准备的
素材）**不建节点也不连线**，报进 `stats.unresolved_references`，由创作者在画布上自行挂。
名字里**点到了条目但项目里没有这条**（ID 写错、或那个条目还没建）才是缺项，报进
`stats.dangling_items`，`board_apply.py` 会因此拒绝导出。

自指槽位（分镜照抄 MOTION 的「起始帧」槽位、指回本镜自己的冻结关键帧）**不连线**：
节点不能喂自己，而 `MOTION → SHOT` 的「分镜」边已经承担了同一个事实。与结构边落成同一对
节点同一端口的参考边只留一条。

`顺序：n` 是引用编号的**唯一来源**，两端都用它：文档正文里的 `<Picture N>` 按 `顺序` 递增，
画布上的引用列表也按 `顺序` 排——导出时写进节点的 `data.referenceOrder`。两者同源，`{{ref N}}`
与 `<Picture N>` 才不会各指一张图。画布上所有参考都进同一个 `in` 端口——视频节点的
`in` 接受图片/视频/音频/文本，**没有**独立的首尾帧输入位，端口一律以 `getCanvasNodes` 返回的
`ports` 为准。结构边（`MOTION` 的「分镜」）在文档里没有 `顺序`，排在声明了顺序的参考之后。
**音色不走这个字段**：它登记在 `MOTION-*` 的「参考音频」行上（VID-27），按行内写的
「角色」接到该人物的对白节点 `in`，不接视频节点（接上去会被当成成片音轨）。
视频片段不作参考输入，写了会记进 `stats.ignored_video_slots`，不静默丢掉。
连线前用 `getCanvasNodes` 的 `ports` 确认端口 ID 与类型，不猜端口名。

**音乐节点不与任何节点连线**：它是时间线层的产出物（VID-14），供剪辑铺轨，不接任何生成
节点的 `in`——单镜产物不自带配乐音轨，把它接进某一镜或视频节点都会破坏这条边界。

## 参考约束随正文一起下发

参考槽位后面那句 `（用途：…；控制：…；不得控制：…）` 不是给创作者看的注释，它是执行端唯一
知道「这张图允许决定什么」的地方：身份参考不得越权定构图，地理参考不得越权定长相。所以导画布时
把它逐条编译成**追加在正文之后的参考约束块**，结构与 `$short-drama-produce` 的编译器一致：

```text
参考约束：
参考 1（卢修斯身份板），用途 身份。允许控制：面部、服装与体态。不得控制：本镜动作与终态。
参考 2（书房场景板），用途 地理。允许控制：书桌方位、窗位。不得控制：人物身份、动作。
```

- 编号取文档那条声明自己的 `顺序`，与正文里的 `<Picture N>` 同源；
- `用途`/`控制`/`不得控制` 照抄文档原词，不翻译、不改写；
- 正文是英文时改用英文章头（`Reference contract:`），字段值仍是文档原词；
- 画面与视频的进 `prompt`，对白的音色参考进 `instruction`；
- 缺 `用途`/`控制`/`不得控制` 的槽位编译不出来，报进 `stats.incomplete_reference_slots`，
  回上游补全——画布不替它编一段。

「参考约束」按**文档的声明**编译，不只按连上的边：某一条还没挂上时它也照写——声明里的编号就是
正文 `<Picture N>` 的编号，漏掉它会让它后面的编号整体错位。画布上的**引用列表**只列实际连上的
节点，所以项目外素材（`unresolved_references`）要由创作者自己挂上；它在文档里不在末尾时，还要
在节点的引用列表里把它拖到对应次序（新挂上的引用默认排在最后）。

画布不写正文——约束块是**追加**，创作者定稿的正文一字不动。片段级素材数超过目标模型一次生成的
上限时（H3：9 图 / 3 视频 / 3 音频）报进 `stats.reference_over_limit`，回分镜阶段按重要性取舍。

## 一次性导出画布

一集几十个节点时，可以不逐个 `addNode`，直接导出整集画布：

```bash
python3 {技能目录}/scripts/board_apply.py <project> --episode <EP> --out <EP>.canvas.json
```

产出由创作者导入工作区。结果与逐个调用画布工具一致，差别只在速度。
**只导出新文件，不修改任何正在打开的画布**：运行中的画布仍然只经画布工具与节点函数改动，
不直接写 JSON。导出用于「首次建图」与「换机重建」，不用于「改动已有画布」。

导出有两道硬门，返回码不同，都要按提示回上游处理：

| 情形 | 退出码 | 处置 |
|---|---|---|
| `dangling_items` 或 `empty_prompts` 非空 | `2` | 计划不完整，回对应 owner 修文档，不在画布上猜 |
| `nodes_without_ratio` 非空（画幅未定） | `3` | 先确认画幅并写入档案；确实要先看节点用 `--allow-missing-ratio` 放行 |

参考没备齐（`unready_references` 非空）**不阻断导出**——节点先立起来，但导出时会把「哪些条目
还不能生成」逐条打出来。项目外素材（`unresolved_references` 非空）同样只报不挡：它不是缺项，
是那些图本就不在项目里，不会出现在连线中。

加 `--structure-only` 时只连结构性边（`MOTION` 的「分镜」）：图片参考边与音色参考节点
全部留到素材产出后补。

## 生成前的确认

**先展示、再确认、后生成**。这是硬闸门，不可合并、不可跳过。

建完节点与连线后，把本次要生成的内容完整列给创作者：每个节点的条目 ID、对象与数量、
目标模型与规格、会话中完整提示词、实际接入的参考、预计执行次数。使用可用的 `askUser` 提问，
没有提问工具时文字提问并等待。

算力统一称「消耗算力」，有可靠报价才展示，查不到就说明「算力消耗未知」。
以下均不构成确认：制作意愿、风格认可、提示词已看过、之前的确认、`继续`/`都做完`/`预算没问题`。

修改任何节点的提示词、参数、连线或数量后，原确认立即失效，重新展示并确认。

## 执行与核对

确认后按已授权范围执行：`node:generateImage` 或 `node:generateVideo`，参数为 `{}`，
使用节点当前配置。生成是后台任务，`generating` 只表示已开始；用 `node:getGenerationStatus`
查询完成结果，`node:cancelGeneration` 停止生成。

一集几十个节点必须**分批**：按镜序切成若干批，每批执行完回报结果再继续，
不一次性发出全部生成。

**提交即算力已花**：生成是后台任务，点下去就开始计费。所以重试前先看这一镜的**节点历史**
（产物落在 `assets/<节点 id>/`，历次结果都在历史记录里）——已经有产出就先用「设为当前结果」
切回去看，**不要直接重投**：原样重投只多花一次算力，不产生任何修复。确认这次真的没出东西，
再重试。

失败按**哪一类被拒**分流，三类改的地方不同，改错了等于白花一次：

| 被拒的是 | 改哪里 |
|---|---|
| 文本 | 提示词正文（画面描述、动作、运镜），不动参数与参考 |
| 参考 | 换一张参考图，或先回上游把这一条补齐（`stats.unready_references`、项目外素材） |
| 音频 | 重录这一句（台词、语气或音色），不动画面 |

生成完成后核对实际产出：图片节点看输出图片，视频节点看输出视频。
只存在文件、只看过静帧，都不等于看过完整结果；未核对的部分如实说明。

## 与生成技能的边界

本技能负责「文档 → 画布 → 触发生成」。上游内容归各 owner：

- 提示词怎么写：`$short-drama-image-prompts`、`$short-drama-video-prompts`（含时间线音乐章节）
- 镜头怎么分：`$short-drama-storyboard`
- 资产与连续性：`$short-drama-assets`
- 台词与录音：`$short-drama-write`

`$short-drama-produce` 走的是项目外的 adapter 路线（`production_tool.py`，含 `tts` 与 `music`
模态），与本技能的画布路线并列。用户要走画布时用本技能——**对白与配乐都在本地画布出声**，
不出钱、不配云凭据；不要在画布之外另建生产通道，也不要把 adapter 凭据带进画布流程。
其他技能正文里「实际生成转 `$short-drama-produce`」的句子，指的就是那条项目外 adapter 路线。
本环境没有可用的 adapter 与凭据，**「实际生成媒体」由本技能承担**：图片、视频、对白音频、
配乐一律在画布节点上生成；读到那些句子时按本技能走，不另起生产通道。
成片剪辑仍归 `$short-drama-edit`。

## 已知限制

- 本环境没有 shell，脚本一律通过 `dramaScript` 执行。本技能提供三个脚本，`skill` 一律填
  `short-drama-canvas`：`board_plan.py`（解析文档出施工计划）、`board_apply.py`（导出画布文件）、
  `board_ratio.py`（读写成片画幅）；其余参数按顺序进 `args`，项目目录用 `projectRoot` 指定。
  引用其他技能的脚本（如 `project_tool.py`）时，`skill` 填脚本实际所属的那个技能名。
- 画布节点存在前端状态里，本技能不直接改画布 JSON，全部经画布工具与节点函数操作。
- 节点类型、函数名、参数结构、可选模型都随实际安装内容变化；每次以 `getCanvas`、
  `getNodeTools`、`node:getConfig` 的返回为准，不使用本文档里的型号或档位当固定值。
